An embedded, append-only key-value database for Java.

BergDB runs inside your Java process, keeps every transaction in one append-only stream of files, and lets you read the database as it was at an earlier time. A value can be any byte array, a Java object, or a schemaless document.

Main ideas

One stream
Data, index and history are all records in the stream: no write-ahead log, no index files. The same transactions in the same order give the same bytes. A start reads only the stream's tail, so the time to open a database does not grow with its size.
History
A read can be made at any time that is still kept, and sees the database as it was then, its indexes included.
Code only
Java code is all that is needed, for the advanced features too: a transaction is a Java method, an index is made by a call, and a query is a loop over Java objects. No query language and no schema files.
Features
Atomic transactions, written in Java code only. Scans of the keys of a directory and of an index, forward and backward. Secondary indexes on the fields of stored objects, and compound ones, on up to 8 fields. Historic queries with every feature of the queries at the current time.
Small
One jar with no dependencies beyond the JDK. No server, few settings.
Proven algorithms
BergDB's core algorithms are proved in Lean. Every transaction is applied whole, and every read, at the latest time or an earlier one, sees the database as it was then, also after a crash and while data is evicted from cache memory.

The Core is a key-value store of byte arrays; the Pub API on top of it adds the Java objects and documents, the path-like keys and the secondary indexes.

Get it

  • The latest release. Each release's jar and the Javadoc of its API are on GitHub Releases, under the release's tag. The latest is release-2026.6.
  • The source. github.com/bergdb/bergdb. With a JDK 17 or later, java/build.sh builds the jar, java/build/bergdb-release.jar.

Try it

You need a JDK 17 or later and the jar. A first program, Hello.java:

import bergdb.pub.Connection;
import bergdb.pub.Database;
import bergdb.pub.Factory;
import bergdb.pub.Time;

public class Hello {
    public static void main(String[] args) throws Exception {
        try (Database db = Factory.database().create("hello-db").start()) {
            Connection c = db.connection();
            Time first = c.put("/fruit/apple", "red").getTime();
            c.put("/fruit/apple", "green");

            // prints green
            System.out.println(c.get("/fruit/apple", String.class));

            // read the past: prints red
            c.setLookupTime(first);
            System.out.println(c.get("/fruit/apple", String.class));

            // wait until durable
            c.sync();
        }
    }
}

Compile and run it with the release's jar beside it:

javac -cp bergdb-2026.6.jar Hello.java
java -cp bergdb-2026.6.jar:. Hello

create opens the database in the directory, or makes a new one if there is none; open only opens an existing one and never makes one.

Stored Java objects, a transaction, an index and a query of the past, in Accounts.java:

import bergdb.pub.*;

public class Accounts {
    // a plain Java class
    public static class Account {
        public String owner;
        public long balance;
        public Account() {}
        public Account(String o, long b) { owner = o; balance = b; }
    }

    public static void main(String[] args) {
        try (Database db = Factory.database().memory().start()) {
            Connection c = db.connection();

            // a secondary index
            db.indexBuilder("by-balance").dir("/acc/")
                    .type("long").field("balance").start().join();

            c.put("/acc/1001", new Account("Ann", 100));
            c.put("/acc/1002", new Account("Bob", 20));
            c.put("/acc/1003", new Account("Cecilia", 60));
            Time before = c.currentTime();

            // a transaction: Ann pays Bob 30
            c.rw(env -> {
                Account from = env.get("/acc/1001", Account.class);
                Account to = env.get("/acc/1002", Account.class);
                from.balance -= 30;
                to.balance += 30;
                env.put("/acc/1001", from);
                env.put("/acc/1002", to);
            });

            // in key order
            for (Account a : c.usePrimary(Account.class).dir("/acc/")
                    .objects()) {
                System.out.println(a.owner + " " + a.balance);
            }

            // by balance: 50 or more, largest first
            for (Account a : c.useIndex("by-balance", Account.class)
                    .from(50, true).backward().objects()) {
                System.out.println("50 or more: " + a.owner + " " + a.balance);
            }

            // the same query, in the past
            c.setLookupTime(before);
            for (Account a : c.useIndex("by-balance", Account.class)
                    .from(50, true).backward().objects()) {
                System.out.println("50 or more, before: " + a.owner + " "
                        + a.balance);
            }
        }
    }
}

Compiled and run like Hello, it prints:

Ann 70
Bob 50
Cecilia 60
50 or more: Ann 70
50 or more: Cecilia 60
50 or more: Bob 50
50 or more, before: Ann 100
50 or more, before: Cecilia 60

Account is an ordinary class with public fields and a public no-argument constructor: a put stores the object, and a get or a scan gives it back as an Account. rw runs its action as one atomic transaction: both puts are made, or neither, and if another transaction changes what the action has read, the action runs again. The index is kept as the data changes, in the same transactions. memory() gives a database in memory, gone when it closes; create, as above, keeps one in a directory.

The API is the packages bergdb.pub and bergdb.pub.util. The README in the repository says what a running database needs and where more examples are.

Status

BergDB has been tested thoroughly, release by release. Whether that is enough for your use is yours to judge: the code, the tests and each release's test results are all in the repository.

How the latest release, 2026.6 (2026-11-24, tag release-2026.6), was tested, on commits near its release commit:

  • 1,738 unit tests, 89 functional tests and 26 longer tests, all passed, on macOS with JDK 27; the unit tests also on an Android emulator.
  • Thousands of kills of a process in the middle of its writes, each followed by a restart that checks every transaction for lost or changed data; crash and power-loss tests of the stream's files.
  • Java's index and reclaim's steps checked, transaction by transaction, against the Lean model, on generated workloads with new seeds each day and on the workloads of the user programs below; Java's own quick, partial check of the writer's contract after every commit of the unit tests and of the user programs' longer runs (4.3 million commits).
  • Programs written against the public API alone, as a user writes them, with their own checks of what they read, also under forced stops: eight new ones for this release.
  • Fuzz tests of the API and of the index, and a run at 10 million keys with reclaim: 100 million transactions.
  • The runs: java/night.sh (3 hours) on main of 2026-11-23, with every change of the release's Java code (a change of the trace checker's C-STEP, in Lean, landed after it, through its gate); java/night.sh and java/week.sh (8 hours) on 2026-11-20 and 21; java/timing.sh against 2026.5. The Java code a user runs did not change after them, but for one comment and the version number. The release notes, section "Verification", list each run and its result.

One bug is known in 2026.6, RB-005, of the least severity: a count that can be short, with no effect within a transaction's limits. 2026.6 fixes the four found in 2026.5 (RB-001 to RB-004; item 033 lists them all). The API and the stored format will likely change before a stable release: a database made by one release may not open in the next (2026.6 refuses those of 2026.5 and earlier). There is no upgrade tool; read the data with the old release and put it with the new one. The main branch moves ahead of the latest release.

BergDB's core algorithms are proved. The writer, reads at the latest and at every earlier time, crash recovery, restarts, eviction and reclaim's cuts are proved in Lean, a language whose checker verifies every step of a proof, for a model of BergDB's Core layer in lean/. The proofs rest on assumptions that are tested instead, among them that Java does what the model does, which the tests check transaction by transaction; the Pub layer, threads and the costs are outside the model. This holds for release 2026.6 and the code on main since 2026-11-19, not for release 2026.5 and earlier, whose writer is older. Item 030-26 says what is proved and what is not; item 030-38 lists what it gives a user, each guarantee proved or tested on purpose.

Known issues. One bug is known in release 2026.6, RB-005 (item 033): a count of the index nodes that a transaction makes dirty can be short for a key transformed to a longer key, with no effect within a transaction's limits. Two things to plan for: the API may change between releases, and the stream format may change between releases.
